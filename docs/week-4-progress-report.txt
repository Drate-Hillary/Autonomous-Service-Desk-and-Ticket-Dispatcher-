KEY DECISIONS

1. Headline decision — resolved the domain conflict. The console (resolv-hq)
   and its AI documentation described a procurement assistant, while the real
   backend and customer app already implemented a support-request triage
   agent. Per the brief's rule that a proposal must solve one clearly bounded
   problem, the project adopted a single use case: the "Resolv HQ Support
   Agent" — grounded knowledge-base Q&A, own-account/request status lookup,
   and drafting an escalation ticket for human approval, never itself
   executing a refund, billing change, cancellation, or account mutation.
   The console was rewritten to match the backend (README, mock-console.ts,
   console-store.ts, the login page, the knowledge page, the dashboard
   subtitle), and the same correction was carried through
   model-selection-note.md, prompt-specification.md, and evaluation-table.md
   — including fixing a pre-existing arithmetic error in the evaluation
   summary. Rewriting UI copy and one demo script was far cheaper than
   rebuilding a schema, tool set, and boundary matrix around procurement, so
   the console moved to match the backend rather than the reverse. Full
   account in docs/domain-conflict-resolution.md; verified with a clean
   `npx tsc --noEmit` and a zero-match grep for procurement-domain language.

2. Kept tool schemas strict rather than permissive. All four tools declare
   additionalProperties:false and explicit required arrays, exceeding the
   brief's minimum of two tools, so the model cannot smuggle in undeclared
   arguments.

3. Scoped draft_escalation_ticket as a genuinely read-only simulated side
   effect (labeled "DRAFT — not submitted", writes nothing) rather than a
   real mutation, deliberately, since a tool named "draft" is the easiest
   one to accidentally make too powerful.

4. Chose to keep extending one living architecture diagram file week over
   week instead of redrawing it each time, so it stays a single traceable
   artifact through Week 7.
